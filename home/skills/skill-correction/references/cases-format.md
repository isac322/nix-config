# 학습 규약 (패밀리 공통)

이 문서는 레지스트리 스킬 전체의 학습 구조를 정하는 유일한 정본이다. 다른 스킬은 "학습 규약은 `skill-correction` 소유"라고만 참조하고 이 내용을 복사하지 않는다. 교정 PR 서브에이전트는 편집 전에 이 문서를 읽는다.

## 규칙 ID

- 형식은 `<PREFIX>-<NN>`이다(예: `TRI-07`). `SKILL.md`의 규칙 bullet 맨 앞에 `**TRI-07**`처럼 굵게 쓴다. 절차 단계 번호와 규칙 ID는 분리한다. 단계는 재배열될 수 있지만 ID는 바뀌지 않는다.
- ID는 재사용하지 않는다. 새 ID는 `SKILL.md`와 `## 규칙 이력`을 통틀어 가장 큰 번호 + 1이다.
- 폐기하거나 대체한 규칙은 `SKILL.md`에서 지우고 `## 규칙 이력`에만 남긴다. 취소선으로 남기지 않는다.
- 의존 스킬(`issue-validation`, `five-whys-root-cause-analysis`, `receiving-code-review`)은 ID 체계가 없다. 섹션 제목으로 지목하고, ID를 새로 붙이지 않는다.

## 가중치 표식

- `SKILL.md`에는 `[U]`만 쓴다. `[U]`는 사용자 지시, 교정, 승인(사용자가 "좋아", "진행해"로 받아들인 제안 포함)에서 온 규칙이며, 사용자 승인 없이 완화·삭제할 수 없다. 규칙 ID 바로 뒤에 둔다.
- 표식이 없으면 에이전트 관례에서 온 기본값이다. 근거가 있으면 교정 없이도 바꿀 수 있다.
- 세부 근거 등급(교정, 명시 지시, 승인)은 `SKILL.md`에 쓰지 않는다. `## 출처 색인`에서 세션·msg id로 추적한다.
- 에이전트 관례는 3회 이상 반복됐거나 빠지면 사용자 교정이 재발할 것만 `SKILL.md` 기본값으로 둔다. 나머지 세부 기본값(길이 예산, 심각도 세부, 템플릿, dossier 형식)은 `references/defaults.md`나 `references/templates.md`에 "바꿀 수 있는 기본값"으로 두고, 쓰는 단계가 그 파일을 명시적으로 읽게 한다.

## 크기와 배치

- `SKILL.md` 목표: 드라이버(TRI, I2P, PRR, LQA, SKC) 약 180줄 이하, 공유(MAC, GHP, DBR) 약 100줄 이하.
- 넘치는 체크리스트, 템플릿, 기본값은 `references/`로 옮긴다. 교정 PR이 목표를 넘기면 그 PR 안에서 분리한다.
- 다른 스킬 디렉터리의 파일 경로를 참조하지 않는다. 스킬은 이름으로만 참조한다.

## `references/cases.md`

각 스킬에 하나 둔다. 실행 중에는 로드하지 않고 교정할 때 `skill-correction`만 읽는다. 파일 첫머리에 이 사실을 한 줄로 적는다. 섹션은 셋이다.

### `## 케이스`

사용자 교정과 사용자가 기대 불일치를 지적한 사례를 기록한다. 증류 시드에는 `[U]` 지시 사례도 넣을 수 있다(아래 "시드"). 발화 하나를 그대로 규칙으로 만들지 않는다(`skill-correction` SKC-34). 시드 이후의 새 명시 지시는 상황·대상에서 적용 조건을 도출할 수 있을 때만 `[U]` 규칙과 출처 색인 행이 되고, 그 상황에만 해당하는 일회성 지시는 케이스로만 남는다. 기각한 제안도 `rejected`로 근거와 함께 남겨 같은 논쟁이 반복되지 않게 한다.

케이스는 nix-config에 반영한 교정(반영 위치 `skill`, `project-reference`)에만 만든다. 반영 위치와 `일반화` 값은 다음처럼 대응한다. `일반화`는 교훈이 적용되는 범위다.

| 반영 위치 (`skill-correction` 제안·분석 결과) | 케이스 | `일반화` |
|---|---|---|
| `skill` | owner 스킬 `cases.md` | `global` |
| `project-reference` | 프로젝트 문서의 `## Cases` | `project` |
| `repo-harness` | 만들지 않음(대상 저장소 지침 안내) | — |
| `memory` | 만들지 않음(memory 저장) | — |
| `out-of-family` | 만들지 않음(instruction-architect 안내) | — |

반영 위치가 `skill`이어도 교훈이 memory·전역 정책과 이어지면 `비고`에 적는다. 스키마의 `memory`, `out-of-family` 값은 기존 케이스를 재분류할 때(예: 적용한 규칙을 memory로 옮김)만 쓴다.

```markdown
### CASE-YYYYMMDD-<slug>
- 상태: applied | proposed | rejected | superseded-by CASE-…
- 출처: <harness> session <8자> msg <id> (공개 가능한 것만)
- 상황: 1–2문장 일반화(요지, 원문 인용 금지)
- 대상: 작업 종류 / 저장소 소유권·가시성 / 산출물 종류 / 위험도
- 적용 조건: 이 교훈이 적용되는 상황·대상의 경계. 일회성이면 "이 사례 한정"
- 사용자 기대: …
- 실제 행동: …
- 원인 분류: wrong | loose | missing | conflict | not-followed / 규칙: <ID>
- 변경: <ID> before → after 요지 | 규칙 유지, 케이스 기록
- 일반화: global | project | memory | out-of-family
- 재발 확인 기준: 다음 실행에서 무엇을 보면 해결된 것인지
```

- `YYYYMMDD`는 사례가 일어난 날짜다. `<slug>`는 영어 소문자 kebab-case로 짧게 쓴다.
- `<harness>`는 `omp`, `claude`, `codex` 중 하나다. `<id>`는 메시지 record id(8자 hex)이고, ask 답변은 `ASK@<ISO 시각(분 단위)>`로 적어도 된다.
- 원인 분류 정의:
  - `wrong`: 규칙이 사용자 기대와 반대 행동을 지시했다.
  - `loose`: 규칙이 있었지만 사용자 기준보다 약했다.
  - `missing`: 해당 규칙이 없었다.
  - `conflict`: 두 규칙(스킬 간 또는 스킬과 가드)이 서로 다른 행동을 요구했다.
  - `not-followed`: 규칙은 맞았는데 실행에서 지켜지지 않았다.
- `대상`과 `적용 조건`은 시드 케이스를 포함한 모든 케이스에 필수다.
- 재발하면 케이스에 `- 재발: <날짜> <harness> session <8자> msg <id>` 줄을 추가한다.

### `## 출처 색인`

모든 `[U]` 규칙마다 한 행을 둔다. 근거는 세션 8자와 msg id(또는 `ASK@시각`)이며 여러 개면 `;`로 잇는다.

```markdown
| 규칙 | 근거 |
|---|---|
| TRI-03 | 01a0ae59 ef4fba96; 01a0d288 ASK@2026-09-25T15:58 |
```

### `## 규칙 이력`

폐기, 대체, 의미 변경만 기록한다. 문구만 다듬은 변경은 적지 않는다.

```markdown
| 날짜 | 규칙 | 변경 | 케이스 |
|---|---|---|---|
| 2026-10-02 | TRI-07 | 폐기, TRI-15로 대체 | CASE-20261001-<slug> |
```

### 시드와 공개 위생

- 새 스킬의 시드 케이스는 증류 작업에서 확인된 `[U]` 교정·지시 사례만 넣고 스킬당 약 10개 이내로 한다.
- 저장소가 공개이므로 `cases.md`와 프로젝트 문서에 다음을 쓰지 않는다: 비밀값·토큰, 로컬 절대경로, hostname, IP, kube context, 테넌트·계정 ID, zone, 고객·조직 내부명, 내부 URL, 비공개 저장소명, 일회성 run ID, 임시 실패 로그, 폐기된 가설, 사용자 발화 원문. 스킬 본문에도 같은 값을 쓰지 않는다(nix-config 정본 경로처럼 저장소가 문서화한 경로는 예외). 출처는 세션 8자와 msg id로만 적는다. 공개 프로젝트 이름(예: flareway, kwin-mcp)은 예시로 허용한다. 일반 예시는 `example.com`, `<owner>/<repo>`를 쓴다. PR 텍스트 위생은 `github-publishing`이 소유한다.
- 기존 `issue-validation`과 `five-whys-root-cause-analysis`의 `references/flareway-cases.md`는 이 형식으로 옮기지 않고 그대로 둔다.

## 승격, 재발, 폐기, 충돌

- 승격: 같은 원인 패턴이 서로 다른 저장소 2곳 이상에서 나오면 프로젝트 reference의 내용을 범용 규칙으로 올리는 안을 낸다. 1곳이면 프로젝트 reference에 둔다.
- 강등: 기본값이 한 프로젝트의 교정과 충돌하면 범용 규칙은 두고 그 프로젝트 reference에 override를 둔다. 같은 override가 2곳 이상에서 생기면 범용 기본값 변경을 제안한다.
- 첫 `not-followed`: 맞는 규칙이 있고 관련 케이스가 없으면 규칙 문구는 바꾸지 않는다. `상태: applied`, `변경: 규칙 유지, 케이스 기록`으로 케이스만 추가한다. 규칙을 절차 체크포인트로 옮기는 것이 분명히 도움이 되면 그 이동만 같이 제안한다. 이 경우 교정 PR에는 케이스 항목만 들어갈 수 있다.
- 재발: `applied` 케이스가 재발하면 규칙 문구를 늘리기 전에 `not-followed`로 판정한다. 그 규칙을 절차의 해당 단계 체크포인트로 옮기거나 description 트리거를 고친다. 세 번째 재발이고 규칙이 권한, 대기, 완료 판정 성격이면 스킬로는 보장할 수 없으므로 `out-of-family`로 보고해 instruction-architect 경로(critical segment 후보)를 안내한다.
- 폐기: 새 교정과 정면 충돌하고 사용자가 교체를 승인한 경우에만 이전 ID를 `## 규칙 이력`으로 보낸다. `[U]` 규칙 폐기는 원 지시를 인용해 명시 승인받는다.
- 스킬 간 충돌: 의미마다 owner는 하나다. owner 스킬만 고치고 다른 스킬의 참조 문구는 참조로 둔다. owner가 불명확하면 `skill-correction` 레지스트리의 소유 범위 열로 정한다.
- 전역 가드와 충돌: 스킬이 진다. 가드 문언 변경이 필요하면 `out-of-family`로 보고한다.

## 드라이버 스킬의 표준 문단

### 프로젝트 훅 (드라이버 `SKILL.md` 0단계, 한 단락)

`gh repo view --json nameWithOwner,visibility`로 대상 저장소를 확인한다. 이 스킬의 `references/projects/<owner>__<repo>.md`가 있으면 먼저 읽는다. 이 위치에는 공개 저장소 문서만 둔다. 비공개 저장소의 프로젝트 사실은 그 저장소의 자체 지침(AGENTS.md, `.agents/skills`)에 두고 nix-config에는 쓰지 않는다. 프로젝트 문서는 기본값을 좁히거나 구체화만 하고 `[U]` 규칙과 전역 가드를 완화할 수 없다.

프로젝트 문서에는 `## Overrides`(규칙 ID 기준)와 `## Cases`(그 프로젝트 케이스)를 둔다. 파일은 첫 프로젝트 교정 때 만든다.

### 교정 루프 (각 스킬 끝, 1–2줄)

결과가 기대와 다르면 사용자는 `skill-correction`으로 이 스킬을 교정할 수 있다. 실행 중 사용자가 교정했다면 따로 묻지 말고 최종 보고에 한 줄로 안내한다.
