## 1. release 스킬 (보류 결정)

- 결정: 이번에는 만들지 않고 여기에 기록한다. 근거 01a0dda6 418e760e(ask 답변).
- 요구 요지:
  - 릴리스 요청은 end-to-end로 처리한다. 대상 SHA의 CI·e2e 게이트 증거 확인 → 마지막 릴리스 이후 모든 커밋 분류 → 버전 결정 → 서명된 annotated tag → push → 파이프라인 완료 관찰 → 게시 artifact 독립 검증. 근거 01a0b53e 0d135ca6; 01a0c7e8 7a3b7a72.
  - 버전은 무엇보다 먼저 사용자와 정한다(기능 추가면 minor, 의존성 수정만이면 patch). 릴리스 노트는 게시 전에 보여 주고 승인받는다. 근거 01a0d288 f30bbae8, b94356a4, b5012508.
  - Helm chart 버전은 앱 태그를 복사하지 않고 실제 chart diff로 판단한다. CRD 안내는 신규 설치와 업그레이드를 구분한다(사용자 교정). 근거 01a0c7e8 39610c51, 4e04b39d.
  - 게시 후 깨끗한 환경에서 README 명령으로 설치해 실제로 써 본다. 근거 01a0d288 b94356a4.
  - 릴리스 노트 구조: 요약, Highlights, 새 기능 표, 설치 명령, Known limitations(미검증 영역 포함), Full Changelog 링크, 업그레이드 주의사항. 모든 주장은 코드와 대조한다. 근거 01a0d288 b5012508(승인).
  - Helm chart도 OCI 레지스트리에 게시하고 GitHub Release를 만든다. multi-arch 빌드는 릴리스에서만 하고 지원 아키텍처는 베이스 이미지를 따른다. 근거 01a095f6 c8dd5251, 0b86cd32.
  - 수정이 main에만 있고 패키지 저장소에 없으면 릴리스가 필요하다고 알리고, 제보자에게 쓸 버전을 알린다. 근거 01a0d288 59de466d. (이슈 종료 댓글의 버전 안내는 `isac-issue-to-pr` 소관)
