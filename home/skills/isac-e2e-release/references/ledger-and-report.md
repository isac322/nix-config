# ledger와 보고 형식

E2V-02, E2V-09, E2V-20, E2V-22, E2V-24, E2V-44의 세부. 바꿀 수 있는 기본값이다. ledger를 쓰거나 보고를 만들 때 읽는다. 단계별 gate 조건과 커버리지 표의 작성법은 `references/state-machine.md`가 소유하고, 여기서는 그 산출물을 어디에 어떤 열로 남기는지만 정한다.

## ledger 원칙

- ledger는 저장소 밖 scratch에 두고, 단계가 바뀌거나 기록이 하나 생길 때마다 갱신한다. 컨텍스트가 압축된 뒤에는 ledger만 읽고 이어서 진행할 수 있어야 한다. 재개·압축 뒤에는 ledger와 함께 SKILL.md·state-machine.md의 현재 단계 절을 다시 읽는다.
- 모든 검증 기록은 실행한 SHA나 산출물, 명령, 범위를 남긴다(E2V-09). run이 만든 산출물은 파일 안이나 파일 이름에 대상 SHA를 새긴다. run이 만들 수 없는 산출물만 ledger 행이 그 대응을 대신 기록한다.
- gate 통과 주장은 ledger 행을 가리킨다. 행이 없는 통과는 통과가 아니다.
- ledger 머리와 각 표, GO/NO-GO·최종 보고는 템플릿의 모든 행·절을 채운다. 해당 없는 행·절은 지우지 않고 "없음"이나 `not_applicable`과 이유를 적는다.
- 채운 brief(`references/briefs.md` 틀)는 scratch 파일로 남기고 경로를 ledger에 적는다. 칸이 빈 brief로 보낸 파견은 무효다.
- 실행 결과는 `ran` / `not_applicable` / `blocked`로 적고, `blocked`를 통과로 세지 않는다(I2P-30).
- 공개 산출물에 쓸 수 없는 값(내부 호스트, 로컬 경로, 비공개 저장소명)은 ledger에만 두고 보고·PR·노트로 옮기지 않는다.

## ledger 머리 (0단계, G-INTAKE)

```text
요청 요약: <사용자 요청 한두 줄 — 조건(멈춤 조건, 범위, 끝까지 위임 여부) 포함>
모드: analysis | qa | release
권한 지도:
  - <행동 또는 PR 종류> → <근거 지시 msg id | 없음: 머지 가드 질문 대상>
  - 예: 수정 PR 생성·머지 → 수정 지시 이후에만 / 릴리스 PR·태그·게시 → <id> / 게시 후 후속 PR 머지 → 없음
릴리스 단위: <단위 이름> — 직전 릴리스 <태그 | 없음>, 버전 소유 <agent | bot | human>
baseline 상태: <단위별 available | none | blocked, 구체화 방법>
후보 SHA: <sha> (기준 브랜치 <branch>)
기준 브랜치 진행 중 변경: <열린 PR 조회 결과 | 없음>
저장소 하네스·프로필: <읽은 저장소 스킬·에이전트·지침 | 프로필 | 없음 — 발견 내용>
환경 사실 재확인: <기억된 사실 → 확인 결과, 닿지 않는 대상은 미검증 범위로>
현재 단계·상태: <단계 번호, gate, 종착 상태 후보>
```

- 권한 지도에 근거가 없는 PR이 있으면 그 PR을 만들기 전에 머지 가드 질문을 미리 보낸다(E2V-02).
- 모드나 권한이 사용자 답으로 바뀌면 머리를 고치고 바뀐 시점의 msg id를 함께 적는다.

## gate 표

게이트 판정 줄은 0단계에 ledger 끝에 복사한 `ledger-checklist.md` 블록 안에 둔다(SKILL.md `## 단계와 게이트`). 따로 gate 표를 만들지 않는다. 재진입 때 블록을 다시 붙이는 규칙도 그 파일 머리에 있다.

## 행 표

### 검증 기록

| 레인 | SHA·산출물 | 명령 위치 | 범위 | 결과 | 상태 |
|---|---|---|---|---|---|
| 후보 전체 스위트 | `<sha>` | <스크립트·로그 위치> | <대상> | <통과/실패 요약> | ran |
| 후보 required CI | `<sha>` | <run 조회 방법> | <job 집합> | … | ran |
| baseline 스위트 × 후보 코드 | `<baseline 태그>` 테스트 × `<sha>` | … | … | <실패마다 의도 변경 대응 + 조기 중단으로 못 한 검사 내용과 그 대체 확인> | ran |
| CI 실행 테스트 vs 저장소 테스트 diff | `<sha>` | … | … | <CI가 안 도는 테스트> | ran |
| 차등 탐색 QA | baseline 산출물 / `<sha>` | <영역별 시나리오 위치> | <표면 영역> | <분류별 건수> | ran |
| 게시 전 공개 문서 설치 | `<sha>`로 만든 릴리스 동등 산출물(빌드 방식·digest) | <설치 기록 위치> | 공개 설치 문서 그대로, 깨끗한 환경 + 변경 목록에서 뽑은 스모크 | <우회 전 실패 기록> | ran |

- 레인 목록과 각 레인의 방법은 E2V-15와 state-machine.md를 따른다. 해당 없는 레인도 행을 남기고 `not_applicable`과 이유를 적는다.
- `게시 전 공개 문서 설치`는 수정 분기가 없는 GO 경로에서도 G-GO 증거이고, 수정이 산출물을 바꾸면 G-REQA에서 최종 head로 다시 돈다(E2V-28, I2P-28).
- baseline이 `none`(첫 릴리스)이면 `baseline 스위트 × 후보 코드`와 차등 탐색 QA의 baseline 쪽은 `not_applicable`(첫 릴리스)로 적고, 탐색 QA는 후보 단일 산출물의 공개 계약 검증으로 기록한다. G-REQA에서도 같다.
- 같은 레인을 다른 SHA에서 다시 돌리면 새 행을 만든다. 이전 행을 덮어쓰지 않는다.
- 수정 분기를 거치면 G-REQA용으로 `baseline 스위트 × 최종 head`, `계약 표면 A/B`, `게시 전 공개 문서 설치(최종 head)` 행을 각각 남긴다.

### finding

| id | 분류 | 발견 방법 | 검증자 | 기존 테스트 커버 | 검증 상태 | 판정 |
|---|---|---|---|---|---|---|
| F-1 | regression | <레인·시나리오> | <발견자 외 에이전트> | 없음 / <테스트 이름> | 재현됨·결함 판정 | FIX |
| F-2 | pre-existing-bug | … | — | … | 미검증 | — |

- `분류`는 ok / regression / new-bug / pre-existing-bug / env-limitation / not-testable 중 하나다(E2V-17).
- `검증 상태`는 `미검증`, `재현됨`, `결함 판정`, `개선(KEEP)`, `문제 아님` 중에서 고른다. NO-GO 근거가 되는 항목만 발견자 외 재현과 결함 판정을 요구한다(E2V-19).
- `판정`은 수정 분기의 닫힌 어휘 FIX / KEEP / DOCS / NOT-A-PROBLEM / UPSTREAM / NEEDS-USER로만 채우고, 수정 지시 전에는 비워 둔다.

### PR

| PR | 종류 | head SHA | 근거 지시 | 리뷰 종료 | 머지 시점 required context | 필수 리뷰 처리 | 머지 SHA | 머지 후 기본 브랜치 CI |
|---|---|---|---|---|---|---|---|---|
| <번호> | 수정 / 릴리스 / 후속 | `<sha>` | <msg id> | <MAC 리뷰-GREEN 루프 종료 라운드, 리뷰한 head SHA> | 전부 보고됨(ruleset 조회 방법) | <보고됨 / 전역 merge 가드 예외 적용 / 대기> | `<sha>` | <결과, 실패면 E2V-31 분류> |

- `머지 시점 required context`는 저장소 ruleset의 required 목록을 실시간 조회해 정확한 head에 보고된 것과 대조해 적는다. "대기 중 없음"만으로 채우지 않는다(E2V-30).
- `필수 리뷰 처리`는 전역 merge 가드가 정한 결과를 그대로 적는다. 가드가 예외를 인정한 경우에도 그 근거를 남긴다. 이 스킬은 리뷰 승인 요건을 따로 정하지 않는다.
- head가 바뀌면 같은 PR에 새 행을 추가한다.

### 게시 단계

단위마다 태그·게시 트리거·릴리스 객체의 소유(agent / bot / 파이프라인)를 먼저 적고, 소유에 맞는 갈래 하나만 쓴다. 단위별 갈래와 순서는 state-machine.md의 게시 절차가 정한다.

**agent 소유 갈래**

| 단계 | 입력 산출물 | 단언 | 결과 |
|---|---|---|---|
| 태그 대상 확인 | `<sha>` | 트리 == 마지막으로 gate를 다 통과한 head 트리, 사이 커밋 == 이번 실행의 수정·릴리스 PR | … |
| 태그 생성·푸시 전 검증 | `<tag>` | 태그 식별(이름이 직전 릴리스 형식, 첫 릴리스면 저장소 선언·workflow에서 정한 형식 + 대상 커밋 + 트리 == 대상 트리). 서명은 프로젝트가 선언한 서명 방식이 있으면 검증 통과, 없으면 `not_applicable`(무서명 정책)로 기록 | … |
| 태그 푸시 | `<tag>` | 검증한 태그만 푸시 | … |
| 게시 파이프라인 | `<run 조회 방법>` | 완료까지 관찰 | … |
| 채널별 공개 확인 | `<채널>` | 모든 배포 파일이 공개 상태(초안·제출 상태 아님) | … |
| 릴리스 객체 | `<tag>` | 검증된 태그에 생성. 파이프라인이 만들면 생성하지 않고 태그를 가리키는지와 초안이 아닌지 확인 | … |

**bot 소유 갈래**

| 단계 | 입력 산출물 | 단언 | 결과 |
|---|---|---|---|
| bot 릴리스 PR 확인(trigger 전) | bot PR head `<sha>` | 게시 전 gate(G-GO, 해당하면 G-REQA, G-CUT, 이 bot PR의 G-MERGE)와 G-PUB의 trigger 전 단언: 트리 == 마지막으로 gate를 다 통과한 head 트리, 머지 대상 커밋이 예정대로, 버전이 버전 근거와 일치, required context가 그 head에 보고됨 | … |
| 머지(게시 trigger) | bot PR | G-MERGE 통과 후 한 번 | … |
| 게시 파이프라인(trigger 후) | `<run 조회 방법>` | 완료까지 관찰 | … |
| bot 태그 확인(trigger 후) | bot이 만든 `<tag>` | 태그 식별(이름 형식 + 대상 커밋 + 트리 == 대상 트리). 서명은 선언된 서명 방식이 있으면 검증, 없으면 `not_applicable`. 만들거나 고치지 않음 | … |
| 채널별 공개 확인(trigger 후) | `<채널>` | 모든 배포 파일이 공개 상태(초안·제출 상태 아님) | … |
| bot 릴리스 객체 확인(trigger 후) | bot이 만든 릴리스 객체 | 검증한 태그를 가리키고 초안이 아님. 만들거나 고치지 않음 | … |

- bot 갈래에서 trigger 후 행과 게시 후 확인(G-POST)은 머지 뒤에만 채울 수 있다. 머지 전 요구는 trigger 전 행까지다.
- 한 단계가 한 명령이고, 실패하면 다음 행으로 가지 않는다(E2V-38). 채널이 여럿이면 채널마다 행을 두고, 실패한 채널은 남은 채널을 막지 않는다(E2V-40).

| 확인 | 대상 | 방법 | 결과 | 분류 |
|---|---|---|---|---|
| 기본 브랜치 CI | 머지 SHA | <조회 방법> | … | ok / flake / 결함 |
| 공개 설치 | 단위가 선언한 공개 배포 채널의 산출물(레지스트리 패키지 / 릴리스 asset과 digest) | 공개 문서 그대로, 깨끗한 환경 | <우회 전 실패 기록> | 사용자 문서 공백 / 환경 한정 |
| 핵심 변경 스모크 | 설치본 | <시나리오 위치> | … | … |

### cleanup ledger (E2V-45)

| 종류 | 식별자 | 만든 명령·msg id(run이 만든 증거) | 삭제 명령 | 생성 시각 | 결과(exit 또는 "신호 대기") |
|---|---|---|---|---|---|

- 정리 대상은 E2V-45대로 run이 만든 임시 자원 전부다. 종류는 전역 temporary-resource-cleanup 가드가 정하고, E2V-45의 목록은 예시다. 만들 때 그 자리에서 행을 더한다.
- ledger, 채운 brief, 프로토콜·결정 파일, 판정 기록, 로그는 증거다. 이들이 든 scratch 디렉터리도 행으로 적되 삭제 신호가 올 때까지 지우지 않고, 옮기면 ledger의 경로를 고친다.
- 삭제는 E2V-45의 신호가 있을 때 가드의 삭제 전 확인을 거쳐 행 단위로 하고 exit를 적는다. 신호 없이 끝나는 `BLOCKED`·`STOPPED_NO_GO`에서는 재개에 필요한 행(수정 브랜치, worktree, 컨테이너·이미지)에 "재개용 보존"이라고 적는다.
- run이 만든 증거가 없는 대상은 행에 넣지 않고 지우지 않으며 최종 보고에 남긴다. PR head 브랜치 행은 만들 때 더하고, 삭제는 E2V-45대로 따로 허락받았을 때만 하며 다른 행과 한 명령으로 묶지 않는다.

### NEEDS-USER

| 질문 | 보낸 시각 | 대기 중인 의존 단계 | 답·msg id | 재개 시각 |
|---|---|---|---|---|

- 답 뒤에 사용자가 같은 항목을 다시 물으면 행을 다시 열고, 그 의존 단계만 다시 멈춘다(E2V-24).

## 사용자 질문 시점

질문 형식, 묶기, 답 재사용은 `isac-decision-brief`(DBR-01, DBR-04, DBR-06, DBR-12)가 소유한다. 이 스킬이 질문을 보내는 시점은 아래뿐이다.

1. 0단계: 권한 근거가 없는 PR의 머지 가드 질문(E2V-02), 구체화할 수 없는 baseline(E2V-07), 이전 릴리스에서 끌어낼 수 없는 게시 절차(E2V-05).
2. NO-GO 보고: 보고와 함께 범위 지시를 기다린다(E2V-20). 요청이 수정과 릴리스까지 이미 맡겼다면 묻지 않는다.
3. 수정 분기: NEEDS-USER 항목은 알게 된 즉시 보낸다(E2V-24). 다른 슬라이스는 멈추지 않는다.
4. GO 직후(release 모드, 3단계 행동 전): 프로필 `## Overrides`를 적용한 뒤의 E2V-35대로 한다(위임이면 생략. 프로필 Overrides가 요구하면 묻는다). 요청이 버전 결정과 끝까지의 릴리스를 함께 명시적으로 맡겼으면 질문을 생략하고, 버전 근거와 릴리스 노트는 최종 보고에 싣고, 노트는 게시 전에 독립 리뷰어가 확인한다(E2V-34). 다만 프로필 Overrides가 정한 조건이 버전 근거 표에 해당하면(조건에 맞는 변경이 버전 근거에 있으면) 위임이어도 그 Overrides가 정한 버전 질문만 버전 제안과 근거를 붙여 한 번 묻고, 답이 올 때까지 3단계(컷)와 그 뒤 단계만 멈춘다. 조건에 맞는 변경이 없으면 묻지 않는다. 위임이 아니면 GO 직후 버전과 노트를 한 번에 묻고 답을 받은 뒤 컷한다(E2V-35). 질문을 보냈으면 답과 msg id를 NEEDS-USER 표에 적고, G-CUT은 그 답 기록이 있어야 통과한다. 각 질문은 자기 시점에 보낸다. 다른 질문을 기다리며 미루지 않고, 아직 시점이 오지 않은 질문(예: 수정 분기를 거친 run의 G-REQA 전 버전 질문)을 당겨 붙이지 않는다. DBR-12 묶기는 같은 시점에 생긴 질문끼리만 적용한다.
5. 게시 후: 권한 지도 밖 후속 PR의 머지 승인(E2V-43).

## GO/NO-GO 보고 (한국어, 2단계 종료)

판정이 NO-GO면 태그, 릴리스 PR, 게시를 만들지 않았다는 사실을 첫 줄에 적는다. GO 보고도 같은 절을 쓰고, 해당 없는 절은 "없음"으로 남긴다.

1. **판정**: GO | NO-GO, 후보 SHA, baseline(단위별 태그와 상태, 첫 릴리스면 `none`). NO-GO면 "태그·릴리스 PR·게시 없음, 범위 지시 대기".
2. **버전 제안과 근거**: 단위별 제안 버전, 공개 인터페이스·동작 delta: 추가 / 제거·이름 변경 / 형식·동작 변경을 각각 적고, 없는 칸은 "없음", 전부 읽은 breaking·mixed 변경, 도전 에이전트와 독립 리뷰어의 판정(E2V-11). 첫 릴리스면 초기 버전의 근거를 적는다. 질문은 release 모드의 GO에서만, 프로필 `## Overrides`를 적용한 뒤의 E2V-35대로 이 절 끝에 싣는다(위임이면 생략. 프로필 Overrides가 요구하면 묻는다). 요청이 버전과 릴리스를 끝까지 맡기지 않았으면 버전·노트 승인 질문을 함께 싣는다. 끝까지 맡겼지만 프로필 Overrides가 정한 조건에 맞는 변경이 버전 근거에 있으면 그 Overrides가 정한 버전 질문만 버전 제안과 근거를 붙여 싣고 노트 승인은 묻지 않는다. 노트는 이때도 게시 전 독립 리뷰(E2V-34)를 거치고 최종 보고에 싣는다. NO-GO와 qa 모드 보고에는 질문을 싣지 않는다.
3. **실행한 검증**: 검증 기록 표의 레인별 SHA, 범위, 결과, 상태.
4. **신규 버그·regression**: finding 표 형식. 각 행에 발견 방법, 검증자, 기존 테스트 커버, 검증 상태를 적는다(E2V-22).
5. **변경 기록에 없는 동작 차이**: 항목마다 개선 판정 질문(고쳐졌나, 더 직관적인가, 더 표준인가)과 그 답(E2V-18).
6. **기존 버그**: baseline에도 있는 결함임을 표시하고, 같은 출처 열을 쓴다.
7. **문서 공백**: 설치·사용 문서와 실제 동작이 어긋난 곳.
8. **미검증 범위**: 돌리지 못한 레인과 이유, `blocked` 대상, 표면 중 스모크만 한 영역, 미검증 finding, 환경 한정으로 분류한 것.
9. **산출물 위치**: ledger, 로그, 시나리오 스크립트 위치(사용자 보고에만, 공개 텍스트에는 넣지 않음).

## 최종 보고 (한국어, 종착 상태에서)

패밀리 한국어 보고 관례(E2I-18, E2Q-16과 같은 형식)를 따른다. 각 항목의 상태 어휘는 I2P-61의 fixed-in-PR / merged / released / deployed다.

1. **한 줄 결과**: 종착 상태(`RELEASED_VERIFIED`, `RELEASED_WITH_FOLLOWUPS`, `PARTIAL_PUBLISH`, `STOPPED_NO_GO`, `BLOCKED`, `ANALYSIS_DONE`, `QA_DONE`, `NOT_APPLICABLE`), 단위별 버전, 남은 후속 수.
2. **게시 결과**: 단위별 태그, 공개 배포 채널(레지스트리 패키지 또는 릴리스 asset과 digest), 릴리스 객체, 채널별 공개 상태와 태그·릴리스 객체를 누가 만들었는지(agent / bot). 부분 게시면 실패 채널과 원인(E2V-40).
3. **버전 근거와 릴리스 노트**: 단위별 확정 버전과 그 근거(E2V-11, 수정 후 재도출이면 E2V-12), 게시한 릴리스 노트 전문 또는 링크와 독립 리뷰 결과(E2V-34). 위임으로 승인 질문을 생략한 실행에서는 이 절이 그 질문을 대신하므로 생략하지 않는다. 프로필 Overrides가 요구해 버전 질문을 했으면 그 답도 함께 적는다(E2V-35).
4. **항목 표**: 항목, 한 줄 증상, 판정, 발견 방법, 검증자, PR·머지 SHA, I2P-61 상태, 들어간 산출물.
5. **산출물 타임라인**: 커밋 순서로, 어떤 변경이 어떤 공개 산출물 안에 있는지 보인다(E2V-44).

   | 순서 | 커밋 | 변경(PR) | 포함된 산출물 | 상태 |
   |---|---|---|---|---|
   | 1 | `<sha>` | 직전 릴리스(첫 릴리스면 생략) | `<직전 버전>` | released |
   | 2 | `<sha>` | 수정 PR | `<이번 버전>` | released |
   | 3 | `<sha>` | 릴리스 PR | `<이번 버전>` | released |
   | — | — | **— 이번 릴리스 경계 —** | — | — |
   | 4 | `<sha>` | 게시 후 문서 PR | 다음 릴리스 전까지 어떤 산출물에도 없음 | merged |

   - 릴리스 경계 행으로 릴리스 전과 후를 나눈다. 사용자가 "릴리스 전에 고쳤나, 후에 고쳤나"를 표만 보고 답할 수 있어야 한다.
6. **다음 릴리스까지 낡은 채 남는 페이지**: 릴리스 시점의 내용으로 고정되는 레지스트리·배포 페이지와 그 차이(예: 게시 후 고친 설치 문서).
7. **검증 기록**: 게시 전 공개 문서 설치(G-GO, 수정이 있었으면 G-REQA 재실행), 수정 head의 재QA(E2V-28), 게시 단언, 머지 SHA마다의 기본 브랜치 CI 결과와 flake 분류(E2V-41), 공개 설치 결과와 분류(E2V-42). 주장마다 run과 SHA를 단다(E2V-33).
8. **합의로 정한 판정**: E2V-46의 판정 지점마다 누가 어떤 근거로 정했는지 한 줄. 저장소 전체에서 클라이언트가 보는 계약을 바꾼 FIX는 사용자 기준(고쳐짐, 더 직관적, 더 표준)에 맞아 합의로 확정했더라도 따로 나열하고, 릴리스 노트의 동작 변경(Behavior changes) 항목과 같은 내용인지 대조한다(E2V-47).
9. **미검증 범위**: 돌리지 않은 테스트(E2V-27), 미검증 finding, `blocked` 대상, 환경 한정 항목, 실제 사용자 환경 중 확인하지 못한 것.
10. **사용자 결정 기록**: NEEDS-USER 질문과 답, 권한 지도 변경, 버전·노트 승인 또는 위임 근거, 프로필 Overrides가 요구한 버전 질문의 답과 msg id(E2V-35).
11. **남은 것**: 후속 PR과 머지 승인 상태, 미릴리스 수정(I2P-60 안내 문구 포함), 외부 블로커.
12. **정리**: `### cleanup ledger`의 행별 결과, 신호를 기다리는 남은 행과 삭제 명령, memory에 저장한 환경 사실(E2V-45). PR head 브랜치는 삭제를 따로 승인받았을 때만 지웠다고 적고, 저장소 자동 삭제는 그렇게 구분해 적는다.
13. **검증됨 / 추론 / 미측정**.

실행 중 사용자가 교정했다면 마지막에 `isac-skill-correction`으로 교정할 수 있다는 한 줄을 붙인다.

## 보내기 전 확인

최종 보고와 GO/NO-GO 보고를 보내기 전에 아래를 모두 확인한다. 하나라도 빠지면 고친 뒤 보낸다.

- 본문이 한국어다.
- 모든 항목에 I2P-61 상태가 있고, 타임라인에 릴리스 경계 행이 있다.
- 모든 finding에 발견 방법, 검증자, 기존 테스트 커버, 검증 상태가 있다. 미검증으로 보고한 finding은 미검증으로 표시돼 있다.
- 미검증 범위 절이 비어 있지 않거나, 비어 있다면 그 이유가 적혀 있다.
- 검증 주장마다 ledger 행(run, SHA)을 가리킨다.
- release 모드 최종 보고에 버전 근거와 릴리스 노트 절이 있다.
