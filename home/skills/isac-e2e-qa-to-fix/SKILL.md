# E2E QA → 수정 → 재검증 루프

배포 환경을 QA하고, 찾은 문제를 이슈로 등록하고, 그 이슈를 해결·머지하게 하고, 수정이 사용자가 정한 반영 지점에 올라가면 같은 QA를 다시 돌린다. 깨끗한 재검증 라운드가 나올 때까지 반복한다. 이 스킬은 오케스트레이터다. 소유 범위: 루프 범위 확정, 라운드 상태 기계와 전이 게이트, 역할 분리, 루프 ledger, 멈춤 조건, 최종 보고.

## 경계

- 단계 안의 규칙은 step 스킬이 소유하고 여기서는 이름과 규칙 ID로만 부른다: QA 인터뷰·위험 고지·승인·격리·이슈 등록·정리는 `isac-live-qa`(LQA), 등록 이슈의 트리아지·수정·PR·리뷰·머지·종결은 `isac-e2e-issue-resolution`(E2I), 토론·병렬은 `isac-multi-agent-consensus`(MAC), 게시는 `isac-github-publishing`(GHP), 질문 형식은 `isac-decision-brief`(DBR).
- E2I의 상태 기계와 종착 상태를 다시 정하지 않는다. 이 스킬은 라운드 전이와, E2I 종착을 루프 상태로 옮기는 대응만 정한다.
- 전역 가드(task-intent, application-code 승인, PR 생성·머지 승인, 리뷰 가드, destructive, verification)는 이름으로만 따른다. 머지는 이 루프를 시작한 지시에 머지가 있을 때만 한다(I2P-53, E2I-01).
- 릴리스는 범위 밖이다. 재검증의 전제로 릴리스를 요구하지 않는다(E2Q-07). 사용자가 루프 끝에 릴리스를 지시하면 새 작업으로 따르고, 절차를 이 스킬에 두지 않는다(E2I-17).

## 0단계: 프로젝트 훅

`gh repo view --json nameWithOwner,visibility`로 대상 저장소를 확인한다. 이 스킬의 `references/projects/<owner>__<repo>.md`가 있으면 먼저 읽는다. 이 위치에는 공개 저장소 문서만 둔다. 비공개 저장소의 프로젝트 사실은 그 저장소의 자체 지침(AGENTS.md, `.agents/skills`)에 두고 nix-config에는 쓰지 않는다. 프로젝트 문서는 기본값을 좁히거나 구체화만 하고 `[U]` 규칙과 전역 가드를 완화할 수 없다.

## 1. 진입과 범위

- **E2Q-01** [U] 진입 조건: 사용자가 배포 환경 QA(탐색 QA 또는 실제 상태를 바꾸지 않는 읽기 전용·dry-run 검증, LQA-14)와, 거기서 나온 문제의 수정, 수정 후 같은 검증의 재실행을 한 흐름으로 요청했다(예: "찾아서 고치고, 방금 한 검증을 다시 돌려, 더 안 나올 때까지"). QA와 이슈 등록만, 또는 이미 머지된 수정의 live 검증만 요청하면 `isac-live-qa`, 이미 있는 이슈 목록 해결만 요청하면 `isac-e2e-issue-resolution`을 쓴다. 문서·설치 경로처럼 작은 대상도 같은 모양이면 이 루프다(수정한 문서의 명령만으로 다시 설치·시연).
- **E2Q-02** 루프 시작 때 한 번 범위를 확정해 루프 ledger 머리에 적는다. `isac-live-qa`의 인터뷰·위험 고지·허용 범위 승인(LQA-02, LQA-03, LQA-05)을 그대로 돌리고, 같은 질문 묶음에 루프 항목을 더한다: (a) 반영 지점(수정이 올라가야 재검증을 시작할 환경, 외부 CD인지 에이전트 조작인지, 확인 방법), (b) 수정 단계의 머지 승인 여부와 범위(E2I-01), (c) 멈춤 조건(기본값 E2Q-12), (d) 반영 지점에 올리는 조작(배포, 검증용 이미지 빌드, 격리 환경 생성)의 허용 범위와 수명. brief가 정한 항목은 묻지 않는다(LQA-03). 루프 중 사용자가 QA 범위를 정정하면 QA list에 케이스를 더하고(LQA-19) 실행 중인 담당자에게 전파한다(MAC-07, E2I-11).

## 2. 라운드 상태 기계

라운드는 다음 순서로만 움직인다. 앞 단계의 종료 조건이 채워지기 전에는 다음 단계로 가지 않는다.

```text
QA(1) 탐색 ─ 이슈 0 ───────────────────────────────────────────────▶ 판정
  │ 이슈 ≥1
  ▼
수정 위임(E2I) ─▶ 반영 ─ 반영할 머지 0 ─────────────────────────────▶ 판정
                   │ 머지 ≥1, E2Q-07 게이트 참
                   ▼
                재검증(N≥2) ─▶ 판정 ─ clean / 대기 멈춤 / 에스컬레이션 ─▶ 정리 확인 ─▶ 최종 보고
                                 └ 재발·신규 이슈 → 수정 위임
```

- `QA(1) 탐색`: `isac-live-qa` run 하나. `재검증(N≥2)`은 E2Q-09·E2Q-10의 재검증 run이다. 라운드 번호는 루프 ledger 행과 같다.
- `수정 위임`: 이번 라운드 이슈 목록을 E2I run 하나로 넘긴다(E2Q-05).
- `반영`: E2Q-02 (a)가 외부 CD면 배포를 기다리고, 에이전트 조작이면 E2Q-08 범위 안에서 올린다(격리 검증용이면 LQA-37). 그다음 E2Q-07 게이트를 판정한다. 이번 라운드에 머지가 0건이면(머지 승인 없음, 모든 이슈가 비수정 종착이나 대기) 재검증 없이 판정으로 간다.
- `판정`: E2Q-11로 이슈의 루프 상태를 정하고 E2Q-12로 멈춤을 판정한다.

E2I 종착의 루프 상태 대응(E2Q-11이 쓰는 값, 루프 ledger `루프 상태` 열과 같다):

| E2I 종착 | 루프 상태 | 다음 |
|---|---|---|
| `머지·종결됨` | `재검증 대기` | 재검증 결과로 `재검증 통과`(종착) 또는 `재발`(E2Q-11, 다음 라운드) |
| `의도된 동작`, 오라클 결함 | `오라클 수정` | 케이스 기대값을 고치면 종착(E2Q-11) |
| `미재현` | `재실행 대상` | 다음 재검증에서 케이스 통과 → `미재현 확인`(종착), 실패 → 증거를 이슈에 남기고 다시 위임 |
| `중복` | 정본을 따른다 | 정본 이슈의 루프 상태 |
| `정보 필요`, `구조 변경 승인 대기`, `PR 준비됨(머지 미승인)`, `기존 PR 있음`, `외부 블로커` | `대기` | 사용자·외부 입력이 오면 그 이슈만 다음 라운드에 다시 위임 |

## 3. 역할 분리

- **E2Q-03** [U] QA 단계는 `isac-live-qa` 역할 규칙(LQA-01, LQA-27, LQA-46)대로 돌고 테스트 도중 즉석에서 고치지 않는다. 수정은 등록된 이슈를 E2I로 넘겨 E2I의 owner가 한다(E2I-08, E2I-09, 단일 대상이면 E2I-20).
- **E2Q-04** 수정 위임은 라운드 단위로 한다. 한 QA run의 이슈 등록과 그 run의 정리가 끝난 뒤 목록을 한 번에 넘긴다. E2I의 중복 정리(E2I-04)가 목록 전체를 한 번에 봐야 하기 때문이다. 사용자가 발견 즉시 수정을 요청하면 그 지시를 따르되, 탐색은 멈추지 않고 이슈 단위로 넘긴다.

## 4. 수정 위임

- **E2Q-05** 등록 이슈 목록을 E2I-01의 대상 이슈로 넘긴다. 함께 넘길 것: 루프 범위의 머지 승인과 범위, 게시 모드, 이슈별 QA 케이스 ID와 재현 절차(LQA-33, LQA-36 형식), 반영 지점. E2I run의 진행·종착은 E2I가 판정하고, 이 스킬은 그 결과를 §2 대응표로 루프 ledger에 옮긴다.
- **E2Q-06** [U] 루프 시작 승인이 모든 라운드의 I2P-06 goal이다. 이후 재검증 라운드에서 드러난 goal 안 결함과 QA fixture·oracle 오류는 I2P-15로 처리한다(오라클 결함 분류는 I2P-01). 필요한 검증은 줄이지 않고 보강한다(I2P-36). goal 밖의 구조 변경만 E2I-12 경로로 멈춘다.

## 5. 반영과 재검증 게이트

- **E2Q-07** [U] 재검증은 다음이 모두 참일 때 시작한다. (1) 이번 라운드에 넘긴 이슈가 모두 E2I 종착 상태이거나 사용자·외부 입력 대기다(E2I-13). (2) 반영 지점에서 실제로 돌고 있는 아티팩트가 이번 라운드의 마지막 머지 커밋을 포함함을 확인했다(LQA-13의 digest·commit 대조, tag만 보고 판단하지 않음). 릴리스를 재검증의 전제로 삼지 않는다. 대기 이슈가 있어도 수정된 이슈의 재검증은 시작하고, 대기 이슈는 ledger에 남긴다.
- **E2Q-08** 반영 지점에 올리는 조작은 E2Q-02 (d)에서 승인된 범위 안에서만 한다. 범위 밖이면 LQA-05 형식으로 무엇을 만들고 어떻게 되돌리는지 묻고, 답을 받기 전에는 해당 이슈의 재검증을 `BLOCKED`로 남긴다.

## 6. 재검증 라운드

- **E2Q-09** [U] 재검증은 직전 라운드의 같은 QA 케이스를 같은 입력·파라미터·seed·절차로 다시 돌린다. 이슈마다 원래 재현 절차가 이제 기대대로 동작하는지, 같은 케이스의 다른 항목이 회귀하지 않았는지 본다. 케이스 분모는 고정한다(LQA-20). 설치·문서 경로면 수정된 공개 절차만으로 다시 설치한다(I2P-28).
- **E2Q-10** [U] 같은 케이스 재실행은 결정적 회귀 확인이지 새 결함 탐색이 아니다. 둘을 ledger와 보고에서 나눈다. goal에 새 결함 탐색이 있으면 재검증 라운드에 새 seed·새 조합·새 표면을 쓰는 경계 있는 탐색 campaign(LQA-21)을 별도 트랙으로 붙인다. 탐색에서 발견한 계약을 어느 테스트 계층에 고정할지는 I2P-34, I2P-35가 정한다.
- **E2Q-11** 판정은 §2 대응표를 따른다. 원래 결함이 다시 보이면, 이 루프가 닫은 이슈는 재발 증거 댓글을 남기고 다시 연다(GHP-11, I2P-57). 사용자가 직접 닫은 이슈는 다시 열지 않고 새 이슈에 링크한다(GHP-13). 새 결함은 LQA 경로로 새 이슈를 만든다(LQA-27, LQA-35). 오라클 결함은 두 갈래다: QA list 케이스의 기대값 결함이면 메인이 근거와 함께 케이스의 의도된 바를 고치고 ledger에 개정으로 남긴다(분모 불변, LQA-20). 저장소의 테스트 harness·fixture 결함이면 E2I로 넘긴다(I2P-01 분류). 머지된 이슈를 재검증 전이라는 이유로 열어 두지 않는다(I2P-58, E2I-14). 재검증은 닫힌 이슈를 다시 여는 경로로만 이슈 상태에 영향을 준다.

## 7. 멈춤과 완료

- **E2Q-12** [U] 멈춤 결과는 셋이다(사용자가 따로 정하지 않았을 때).
  - `clean`: 한 재검증 라운드에서 `대기`가 아닌 이슈의 케이스와 나머지 케이스가 모두 기대대로 통과하고, 탐색 트랙이 있으면 새 결함이 0이고, 재오픈이 0이고, `대기` 이슈가 없다. 1라운드 QA가 이슈 0이어도 `clean`이다. 루프는 이것을 목표로 라운드를 반복한다.
  - `대기 멈춤`: 남은 이슈가 모두 `대기`다. 반영할 머지가 0인 라운드도 여기로 온다. 최종 보고에 대기 목록과 필요한 결정(머지 승인 포함)을 `isac-decision-brief` 형식으로 올리고, 답이 오면 그 이슈부터 재개한다.
  - `에스컬레이션`: E2Q-13.
  요청 범위 안의 기능·지원 누락은 멈춤 사유가 아니라 수정 항목이다(범위 조사는 I2P-03). 그런 누락이 남아 있으면 `clean`도 `대기 멈춤`도 아니다.
- **E2Q-13** 같은 결함이 연속 두 라운드 재발하거나 같은 실패로 제자리를 돌면 반복하지 않고 원인을 분리해 결정 필요 항목으로 올린다(`isac-decision-brief`). 에스컬레이션은 goal 밖 구조 변경(E2I-12)이나 이 제자리 돌기에만 쓴다(E2Q-12의 범위 안 누락은 제외).

## 8. 정리

- **E2Q-14** [U] 모든 QA·재검증 라운드는 끝날 때 자기 임시 리소스를 정리하고 정리를 검증한다(LQA-38, LQA-50, IaC 리소스는 LQA-39). 다음 라운드는 새 run prefix와 새 ledger로 시작한다(LQA-16). 반영 지점용으로 만든 격리 환경과 검증용 아티팩트도 E2Q-02에서 정한 수명이 끝나면 같은 방식으로 회수한다. 전체 흔적 조사·목록 보고 요청은 LQA-40, 중지되면 LQA-47을 따른다. 정리 조사에서 나온 제품 결함 의심은 다음 라운드 QA 후보로 넘긴다.

## 9. 병렬과 ledger

- **E2Q-15** 병렬은 단계마다 해당 스킬 규칙을 따른다: QA 케이스는 LQA-23, 이슈는 E2I-08, 항목 owner 원칙은 MAC-03. 라운드는 직렬이다(재검증은 반영 게이트 뒤에만 가능). 루프 ledger는 저장소 밖 scratch에 두고 라운드마다 갱신한다(compaction·재개 후에도 이어 쓴다). 형식은 `references/loop-ledger.md`이고, LQA run ledger와 E2I ledger는 각 스킬이 소유하며 여기서는 ID로만 가리킨다.

## 10. 최종 보고(한국어)

- **E2Q-16** 최종 보고 형식은 `references/loop-ledger.md`를 따른다. 상태 어휘는 I2P-61, 단계별 세부 보고는 LQA-43과 E2I-18을 따르고, 확인한 계약은 주기적으로 다시 돌릴 수 있는 형태로 남긴다(LQA-36).

## 완료 조건

E2Q-12의 멈춤 결과 중 하나에 도달, 모든 라운드 정리 검증 완료(E2Q-14), 루프 ledger와 최종 보고 작성.

결과가 기대와 다르면 사용자는 `isac-skill-correction`으로 이 스킬을 교정할 수 있다. 실행 중 사용자가 교정했다면 따로 묻지 말고 최종 보고에 한 줄로 안내한다. 학습 규약은 `isac-skill-correction` 소유다.
