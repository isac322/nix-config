# Temporary resource cleanup

- When you create a temporary resource for a task (git worktree, branch, fetched temporary ref such as `refs/tmp/*`, or stash; scratch directory or file; cache or generated artifact; container, VM, or local database cluster; background process or preview server; temporary namespace; cloud or Kubernetes object; or a retained Camofox browser tab), record it in your cleanup-resource ledger before or in the same command that creates it. Tell the user the ledger path when you create the ledger.
- A scratch file is any file you write outside the repository that is not a deliverable the user asked to keep, including redirected command output and logs (`> /tmp/x.log`, `tee`), drafts such as PR or issue bodies passed to `--body-file`, and downloaded or generated fixtures. Write these inside one recorded scratch directory for the task when you can, so a single entry covers them; otherwise record each file before or in the same command that creates it.
- Keep the cleanup-resource ledger at `~/.cache/cleanup-ledgers/<workspace>--<session-id>--<task>.jsonl`. `<workspace>` is the basename of the session's working directory. `<session-id>` is the top-level session ID your harness exposes (OMP: `$PI_SESSION_ID`); if it exposes none, generate one when you create the ledger and reuse it for the rest of the session. Never put the ledger in the repository, `/tmp`, `/data/tmp`, or a directory it tracks, and never write a ledger whose filename names another session.
- When the user has you continue work that an earlier session started, append a `link` record with `"mode":"takeover"` pointing to that session's ledger; its open entries become yours to clean.
- A skill may keep its own workflow or run ledger and mirror cleanup rows in it, but every resource must also be in the cleanup-resource ledger, which is the only record cleanup relies on.
- The ledger is append-only JSONL, one JSON object per line, so values are escaped and never split. Each record has `time`, `type`, and the fields of its type, for example:
  - `{"time":"2026-11-18T12:00:00Z","type":"add","entry":"7f3c9a1e","kind":"scratch-directory","id":"/tmp/task-x","session":"01a1cdcd","delete":"rm -rf /tmp/task-x"}`, where `entry` is a random value you generate for each `add` and never reuse
  - `{"time":"2026-11-18T13:00:00Z","type":"removed","entry":"7f3c9a1e","id":"/tmp/task-x","source":"/Users/me/.cache/cleanup-ledgers/repo--01a1cdcd--task-x.jsonl"}`, appended to your own ledger only after the deletion succeeded; `source` is the ledger holding the `add` record
  - `{"time":"2026-11-18T12:05:00Z","type":"link","mode":"child","ledger":"/Users/me/.cache/cleanup-ledgers/repo--01a1ce00--task-x.jsonl","session":"01a1ce00"}`, with `mode` one of `child`, `parent`, or `takeover`
  Write ledger paths as absolute paths. Use exact identifiers (path, name, context and namespace, PID, or Camofox `userId`/`sessionKey`/`tabId`), never wildcards or partial IDs. Append with `>>` or append mode; never rewrite, truncate, or replace the file with a whole-file write, and never write a linked ledger.
- Only the top-level agent writes its cleanup-resource ledger. In-process subagents never create, write, or edit any cleanup-resource ledger: each delegated task that may create resources must tell the subagent to list every resource it created (with the record fields above) in its final result, and the parent appends those records as soon as the result arrives, before doing anything else. If a subagent fails, is cancelled, or returns no resource list, append an `unreported` record such as `{"time":"2026-11-18T12:10:00Z","type":"unreported","entry":"b41d07c2","agent":"QaRunner","paths":["/tmp/task-x/qa"]}`. At cleanup, search every resource kind listed in the first rule for what that subagent may have created and treat what you find as sweep candidates; append `{"time":"2026-11-18T13:10:00Z","type":"resolved","entry":"b41d07c2"}` only after each of those candidates is removed or reported to the user as unresolved. A separate top-level session that you start keeps its own ledger; when you start it, append a `link` record with `"mode":"child"` for it, and have it append a `link` record with `"mode":"parent"` naming your session and ledger.
- Delete ledger entries only after the user says the task is finished, or when the user's request names cleanup as its final step and every other deliverable is done and verified. Never decide on your own that the task has ended; finishing your steps, merging, or yielding is not that signal.
- To clean up, read your ledger and every ledger reachable through `child` and `takeover` links (never `parent` links), keeping a visited set of ledger paths so none is read twice. An `add` record is open until some read ledger has a `removed` record with the same `entry` and `source`. Accept a `child` link only when the child ledger has a `parent` link naming your session, and a `takeover` link only when the linked ledger's filename and its `add` records carry the session ID in the link; report a missing, unreadable, unconfirmed, or cyclic link as unresolved rather than as proof of ownership. Do not read other sessions' ledgers that are not linked. Then sweep for unrecorded candidates: the workspace's extra git worktrees, branches, `refs/tmp` refs, and stashes; task-related paths under `/tmp`, `/data/tmp`, and `~/.cache`; containers; and processes started from the task's paths. A sweep result is a candidate, not proof of ownership.
- Before deleting anything, whether a ledger entry or a sweep candidate, confirm its exact identity, that this session, one of its in-process subagents, or an accepted linked session created it, and that nothing else uses it. For a proven-owned sweep candidate, first append an `add` record for it in your own ledger with a new `entry`. Then delete exactly that resource and append a `removed` record. Never delete anything that is pre-existing or production, shared with other work or sessions, or whose ownership you cannot prove: append an `unresolved` record such as `{"time":"2026-11-18T13:20:00Z","type":"unresolved","entry":"c9e2f415","id":"/tmp/task-x-old","evidence":"name matches task; no creation record"}`, list it for the user with its evidence, and wait. It stays open until, after the user decides, you append a `removed` record with the same `entry` or a `kept` record such as `{"time":"2026-11-18T14:00:00Z","type":"kept","entry":"c9e2f415","id":"/tmp/task-x-old","reason":"user said to keep it"}`. Report owned resources cleaned and unresolved candidates separately; never say everything is cleaned while a candidate is unresolved.
- The local Camofox daemon (`org.nix-community.home.camofox-browser` on `127.0.0.1:9377`, `userId="omp"`, and its Camoufox browser process) is shared across concurrent sessions: never stop, kill, restart, or wipe the shared `omp` session (`launchctl kickstart`, `kill`, `POST /stop`, or `DELETE /sessions/omp`) without the user's explicit prior approval; clean up only this session's recorded `tabId`s (`mcp__camofox_close_tab` or `DELETE /tabs/<tabId>?userId=omp&sessionKey=<sessionKey>`) or `sessionKey` group (`DELETE /tabs/group/<sessionKey>?userId=omp`). If detached browser windows remain or `camofox-browser.log` repeats `"session empty after tab reaper, closing"`, check whether other sessions are using Camofox and ask the user before restarting the service.
- Without a cleanup signal, report completion with every open `add` and `unresolved` record, every `unreported` record without a matching `resolved`, and every link you could not accept, then wait for the user's instruction.
