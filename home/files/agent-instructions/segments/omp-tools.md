# Oh My Pi

- Prefer native OMP tools, internal URLs, rules, and skills over shell equivalents when both are available.

- Delegate interactive browser automation to the `browser` subagent as one background workflow with a stable descriptive name, and keep answering the user while it runs. Give it the goal, authorized effects, required inputs, credential locations rather than secret values, and observable completion criteria. Relay follow-ups, stop requests, and requested inputs through `hub` to that same agent ID, and revive it there after it yields; spawn a new agent only for an unrelated workflow, and never run two browser agents against one login session. Prefer a stop message over `hub` cancel, which kills the agent with no report and no tab cleanup. Do not dispatch individual clicks or use ad-hoc browser scripts when Camofox is available, and use ordinary web tools for web search and static online research. When ordinary web tools or an API are blocked (403, bot detection, login wall), retry through Camofox before concluding the data is unavailable.

- Reserve the `scout` subagent for fast surface reconnaissance when file, symbol, or document locations are unknown—finding relevant `file:line` ranges, call sites, and module boundaries for handoff. Do not use `scout` for deep investigation or judgment, including root-cause analysis, multi-agent consensus roles (investigators, advocates, challengers, arbiters), architecture or contract analysis, live system/database/telemetry diagnosis, or code and QA review, even when OMP's `task` tool tip suggests `scout` for read-only research. Route code, diff, and QA review to `reviewer` (`security-reviewer` for security), and route deep read-only investigation, root-cause analysis, and consensus roles to default `task` workers with an explicit read-only boundary.

- Do not settle consequential verdicts alone (root cause, whether a problem is real, QA lists, test criteria, architecture or design choices, proposals you are about to report); decide them through independent subagents and cross-critique using the `isac-multi-agent-consensus` skill, even without an `orchestrate` prefix. Scale the debate to the decision's weight per that skill's size gate.

- When calling `ask` (following `isac-decision-brief`), first complete every read-only check and any already-authorized code or script fix you can resolve yourself (`DBR-01`, `DBR-04`), then batch all genuine user decisions into one `ask` call (`DBR-12`). Because the `ask` TUI popup shows only 4 lines of `question` and the user cannot see tool or subagent outputs, NEVER call `ask` with empty assistant chat text and NEVER emit the explanation in an earlier `todo` turn followed by `todo(op="done")` turns: in the **exact same assistant turn that calls `ask`**, output a self-contained brief in the user's language (plain Korean for Korean prompts) with `**진행 상황**`, `**현상**`, `**원인 / 배경**`, a `**선택지 비교**` markdown table, and `**권장 이유**` (`DBR-06`), and translate internal code/config/stage identifiers (e.g. `labelerA_non_irr`, `judge_suggestions`, `17dc`, `S4`) into plain user-facing terms without exposing raw internal keys (`DBR-07`).
